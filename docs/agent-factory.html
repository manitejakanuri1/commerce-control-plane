Proposed architecture · agent factory

Agent Factory

A command centre takes a sentence, works out which job it is, and builds a dedicated agent for it — with its own scoped key, its own prompt, and only the tools that job needs. Each agent is reachable as an API.

01

The command centre

A user arrives and types something plain. Nothing is selected from a menu first — the sentence is the input.

USER “Integrate Razorpay with my website”
new INTENT ROUTER reads the sentence, picks the job · asks only what it still needs to know
CLARIFY “How did you build your site?” Claude · Cursor · Codex · something else
new AGENT FACTORY builds one agent for this task and nothing else
SCOPED KEY issued per agent
SYSTEM PROMPT for this job only
TOOL SET least privilege
AGENT INSTANCE runs the task · reachable at its own endpoint
POLICY GATE anything touching money or a merchant's data passes through the same deterministic checks
RESULT structured output, plus an audit record of what the agent did and why
02

One agent per job

Not one large agent with every capability. Each job gets an agent that holds only what that job needs, so a compromised or confused agent has a small blast radius rather than a total one.

AgentJobTools it holdsState
database Connect to a merchant's database and read product detail — name, cost, MRP, stock, everything connect, verify, describe schema, fetch product build first
integration Produce a ready-to-paste prompt for the user's coding tool detect stack, issue keys, render prompt proposed
catalog Import and normalise a storefront's products import, validate, sync vectors exists
commerce Propose what to sell, priced and policy-checked retrieve, propose, evaluate policy, quote exists
reconciler Resolve payments the system has lost track of read provider state, adopt it exists

The last three already run. What the factory changes is how they are addressed: each becomes a named agent with its own key and endpoint, rather than a step inside one fixed pipeline.

03

The database agent

The one to build first, because it is the one every other agent depends on and because most of its engine already exists in the read-only connector.

CALLER “What do we know about sku e1?”
POST /v1/agents/database/run agent key resolved to a merchant and a scope
DATABASE AGENT plans which tools to call, in what order
CONNECT read-only role
VERIFY attempts a write, expects refusal
DESCRIBE what it can actually see
PROJECTION cost and customer data answer the caller · neither is placed in a model's context
STRUCTURED RESULT name, cost, MRP, stock, category, everything the merchant granted

What comes back

POST /v1/agents/database/run
{"task": "everything about sku e1"}

{
  "sku": "e1",
  "name": "Wireless Noise-Cancelling Earbuds",
  "price_paise": 249900,
  "mrp_paise": 499900,
  "cost_paise": 168000,
  "stock": 12,
  "category": "Electronics",
  "source": "merchant database, read-only",
  "reached_a_model": false
}

That last field is not decoration. Cost and MRP go back to whoever asked, and are never placed in a prompt — because the agent reads merchant-written product text, and one of those descriptions already tries to hijack it.

04

Every agent gets its own key

A key is issued when the agent is created and dies with it. Scope is decided by the job, not by who is asking.

ScopeHeld byMayMay never
browseStorefront pagesSearch, ask for a proposalMove money
readThe database agentRead a merchant's granted tablesWrite anything
catalogThe integration agentImport and sync productsCreate payments
fullA merchant's own serverPurchase, reconcile, everythingLeave that server

This already works for two of the four. The browse key sits in the deployed landing page's source, and /v1/purchase answers it with a 403.

05

What exists, what does not

Already running

The engine of every agent

Read-only connector with verified capabilities, policy engine, catalog import, retrieval, reconciliation, scoped keys, audit trail. All deployed and covered by 63 tests.

To build

The factory itself

An agent registry, per-agent key issuance, a spawner, and the intent router that turns one sentence into the right agent. Days rather than hours.

To build first

The database agent

Wraps the existing connector as a named, API-addressable agent. Demonstrates the whole pattern with one working example. Hours rather than days.

06

Order of work

  • Database agent — the one named above. Reuses the connector, proves the pattern, ships today.
  • Agent endpoint shape — POST /v1/agents/{name}/run, so every later agent has a door already built.
  • Per-agent key issuance — extends the two scopes that already exist.
  • Integration agent — renders a ready-to-paste prompt for Claude, Cursor or Codex.
  • Intent router — the sentence-to-agent step. Last, because it is worthless until there are several agents to route between.

Against a deadline: one working agent plus this diagram is a stronger submission than a factory with nothing running inside it. The pattern is what a reviewer evaluates; the scaffolding is what they assume you can add.

Proposed extension to the Commerce Control Plane. The commerce, catalog and reconciliation agents already run in production; the factory reframes how they are addressed and adds the database and integration agents alongside them.
